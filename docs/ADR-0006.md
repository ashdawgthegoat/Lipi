# ADR-0006 — Clinical Workflow UX & Interaction Design

**Status:** Accepted
**Date:** 2026-09-05
**Sprint:** Sprint 5

---

## 1. Context

Sprints 1–4 established Lipi's overall architecture, patient and clinical record model, Vault/storage architecture, and canonical `.lipi` clinical document format.

The primary clinical workflow is therefore already defined.

Sprint 5 focuses on the **user experience and interaction model** through which that workflow is exposed to the doctor.

The central UX goal is:

> **Navigation should be intuitive. Writing should feel natural.**

Lipi is designed primarily for doctors using a tablet with a stylus. The prescription-writing workspace therefore receives specialized interaction decisions that differ from conventional application interfaces.

Sprint 5 intentionally does not revisit previously accepted architectural decisions.

---

## 2. Primary User Flow

Lipi's primary application flow is:

```text
First Launch
    ↓
Doctor Setup
    ↓
Prescription Template Selection
    ├── Upload custom prescription Photo/PDF
    └── Select default prescription
    ↓
Patient Screen
    ├── Patient List
    └── Search
    ↓
Patient Workspace
    ├── Previous Prescriptions
    └── New Prescription
    ↓
Prescription Workspace
    ├── Write / Edit
    ├── Automatic Save
    └── Optional PDF Export
```

### 2.1 First Launch

On fresh installation, the doctor is introduced to an initial setup flow.

The doctor provides basic information about themselves and selects the prescription template to use.

The template may be:

* A doctor-provided prescription image/PDF.
* Lipi's default prescription template.

After setup, the doctor reaches the patient screen.

### 2.2 Patient Screen

The patient screen is the primary application workspace after initial setup.

It provides:

* A list of patients.
* A search facility for locating a specific patient.

Patient discovery remains explicit and doctor-controlled.

### 2.3 Patient Workspace

Selecting a patient opens that patient's workspace.

The workspace provides access to:

* Patient information.
* Previous prescriptions/consultations where available.
* The ability to begin a new prescription.

For a first-time patient, the prescription history may naturally be empty.

The doctor is not forced to inspect historical records before beginning a new prescription.

The doctor may either:

1. Start a new prescription immediately.
2. Review previous prescriptions first and then create a new prescription.

### 2.4 Prescription Workspace

The prescription workspace is the most interaction-sensitive part of Lipi.

The doctor can write or edit the prescription using the tablet and stylus.

The document is automatically saved during the workflow.

PDF export is an optional secondary action and does not replace the canonical `.lipi` document.

---

## 3. Navigation Design

Lipi's navigation should remain simple and predictable.

The application should avoid unnecessary screens, nested navigation structures, or complex interaction patterns.

The primary conceptual hierarchy is:

```text
Patients
    ↓
Patient
    ↓
Prescription History
    ↓
Prescription
```

However, the doctor should be able to move from a patient directly into a new prescription without being forced through the history first.

The interface should communicate the current context clearly so that the doctor understands:

* Which patient they are currently viewing.
* Whether they are viewing historical material or working on a new prescription.
* Where they can return.
* Whether their current work has been saved.

---

## 4. Prescription Interaction Model

Prescription writing is intentionally **stylus-first**.

Lipi assumes that the primary prescription-writing environment consists of:

> **Tablet + Stylus**

This is a deliberate product constraint rather than a limitation that Lipi must attempt to eliminate.

### 4.1 Stylus

The stylus receives primary treatment inside the prescription-writing workspace.

The stylus should be used for:

* Handwriting.
* Drawing/ink interaction.
* Direct interaction with prescription content where appropriate.

Lipi should avoid requiring the doctor to repeatedly switch between explicit "pen modes" merely to write naturally.

### 4.2 Finger

Finger interaction is primarily used for navigation rather than handwriting.

The intended distinction is:

```text
Stylus → Create / Write
Finger  → Navigate
```

This separation allows the writing surface to remain natural while preserving intuitive tablet navigation.

### 4.3 Gestures

The prescription canvas uses a deliberately small and intuitive gesture vocabulary.

| Input                  | Interaction                   |
| ---------------------- | ----------------------------- |
| Stylus                 | Handwriting / ink interaction |
| Pinch in/out           | Zoom                          |
| Single-finger movement | Pan / navigate canvas         |

Lipi should prefer familiar tablet interactions over introducing application-specific gestures without a strong usability reason.

---

## 5. Handwriting Experience

Handwriting is a core interaction rather than a secondary input method.

The prescription workspace must prioritize:

* Smooth handwriting.
* Natural stylus interaction.
* Reliable stylus alignment with the document.
* Minimal interaction friction.
* Preservation of the existing canonical digital-ink architecture.

Sprint 5 does not replace the Excalidraw-based ink architecture established in Sprint 0 or the InkML/document architecture established in Sprint 4.

The UX layer is responsible for making the existing handwriting system feel natural to the doctor.

---

## 6. Automatic Saving

Prescription work should be automatically persisted.

The doctor should not need to consciously manage manual save operations during ordinary writing.

The intended interaction is:

> **Doctor writes → Lipi saves.**

The doctor should not have to wonder whether their handwriting has been saved before leaving the workspace.

The exact implementation of persistence remains governed by the `.lipi` and Vault architecture established in previous ADRs.

---

## 7. PDF Export

PDF export is an optional action available after or during prescription work where appropriate.

The exported PDF is a derived representation.

The canonical editable `.lipi` document remains authoritative.

The UX should therefore treat:

```text
Save → automatic
Export PDF → optional
```

rather than making PDF generation part of the required completion process.

---

## 8. Patient Record Deletion

The doctor must be able to explicitly delete a patient's record.

This is necessary because a patient may visit only once and the doctor may subsequently decide that the patient record should no longer be retained.

Deletion is **doctor-controlled**.

Lipi must not automatically remove patients merely because they have not returned for a period of time.

The deletion interaction must:

1. Clearly identify the destructive nature of the action.
2. Require explicit confirmation.
3. Remove the patient record and the clinical records associated with that patient according to the Vault/data model.
4. Never silently delete clinical records.

The rationale is data ownership and doctor control rather than automatic storage optimization.

An archive mechanism is not introduced by this ADR.

---

## 9. Historical Prescription Interaction

Opening a historical prescription and editing it are distinct concepts.

Sprint 5 identifies this as an interaction requiring explicit validation rather than silently assuming that historical records should always be directly editable.

The UX must distinguish between:

* **Viewing a previous prescription for historical context.**
* **Creating a new prescription based on previous clinical context.**
* **Intentionally modifying an existing historical prescription.**

The final interaction for historical prescription editing should be validated against actual doctor workflow before being treated as a definitive UX rule.

This is an explicit candidate for validation during the **Dad Test**.

---

## 10. Themes

Lipi should support a themeable application interface.

This is a presentation-layer capability and does not alter the underlying clinical data, `.lipi` format, or domain architecture.

The default theme should prioritize:

* Professional appearance.
* Legibility.
* Calm visual hierarchy.
* Clinical usability.

Additional expressive themes may be provided in the future.

A theme may therefore be visually unconventional—even something like a **16-bit/retro-inspired theme**—provided that it does not compromise:

* Readability.
* Accessibility.
* Clinical usability.
* Interpretation of clinical information.

Theme support is established as a product/UX direction but is **not a major implementation requirement of Sprint 5**.

---

## 11. Interruption & Safety Principles

The UX must avoid situations where the doctor can unintentionally lose active clinical work.

In particular:

* Active prescription work should be automatically saved.
* Navigation away from active work must not silently discard changes.
* Destructive actions must require explicit confirmation.
* Historical records must not be modified accidentally.
* Export failure must not imply loss of the canonical `.lipi` document.
* The interface should make current patient/document context clear.

Clinical decisions remain entirely under the doctor's control.

Lipi does not diagnose, recommend treatment, or make clinical decisions as part of this UX architecture.

---

## 12. UX Design Principles

Sprint 5 establishes the following principles:

### Navigation should disappear into intuition.

The doctor should be able to understand the application hierarchy without learning a complicated interface.

### Writing should disappear into the stylus.

The prescription-writing interface should minimize software-mediated friction between the doctor's hand and the prescription.

### Stylus creates; finger navigates.

The primary input roles are intentionally separated.

### Doctor decides.

Lipi should assist the doctor's workflow without silently making decisions about patients or records.

### Clinical records remain authoritative.

UI themes, PDF exports, and presentation choices must never alter the meaning or canonical representation of clinical data.

### Explicit actions for destructive operations.

Deletion and other irreversible operations require deliberate doctor interaction.

---

## 13. Validation — The Dad Test

The final UX should be validated through real-world use by a doctor.

The primary validation target is whether a doctor can perform common tasks without being taught the interface.

Suggested tasks:

1. Find an existing patient.
2. Search for a patient.
3. Open the patient's previous prescription.
4. Start a new prescription directly.
5. Write naturally using the stylus.
6. Zoom the prescription using pinch gestures.
7. Pan the prescription using a single finger.
8. Leave the prescription and return later.
9. Find the saved prescription again.
10. Export a PDF when desired.
11. Delete a patient record intentionally.

Observation should focus on:

* Hesitation.
* Wrong taps.
* Unclear navigation.
* Gesture confusion.
* Writing friction.
* Uncertainty about saving.
* Accidental destructive actions.
* Confusion between historical and current prescriptions.

The UX is successful when the doctor can perform the common workflow with minimal instruction and without having to think about the software itself.

---

## 14. Scope

### In Scope

* Primary navigation UX.
* Patient → patient workspace → prescription navigation.
* Prescription workspace interaction.
* Stylus-first interaction.
* Finger-based navigation.
* Pinch-to-zoom.
* Single-finger panning.
* Handwriting interaction experience.
* Automatic-save UX.
* Optional PDF export UX.
* Patient deletion UX.
* Themeability as a product/UX direction.
* Historical prescription interaction validation.
* Doctor usability validation.

### Out of Scope

* Re-designing the domain model.
* Re-designing the Vault architecture.
* Re-designing SQLite/storage architecture.
* Re-designing the `.lipi` format.
* Re-evaluating the ink engine.
* AI functionality.
* Cloud synchronization.
* Hospital workflows.
* Advanced clinical decision support.
* Advanced search.
* Generalized plugin architecture.
* Full theme implementation/asset library.
* Large-scale visual design-system work.

---

## 15. Decision

Lipi will use a **simple, patient-first navigation model** with the patient screen serving as the primary application workspace after initial setup.

Prescription writing will receive a specialized **stylus-first tablet interaction model**, with:

* Stylus for writing.
* Finger for navigation.
* Pinch gestures for zoom.
* Single-finger movement for panning.
* Smooth handwriting as a core UX requirement.
* Automatic saving as the default persistence behavior.

PDF export remains optional and secondary to the canonical `.lipi` document.

Doctors retain explicit control over patient-record deletion.

Lipi will be designed to support application themes without allowing visual customization to compromise clinical usability or the integrity of clinical data.

Historical prescription editing remains an explicit UX question to be validated against real doctor workflow.

This ADR defines the UX direction without reopening architectural decisions already accepted in Sprints 0–4.

---

## 16. Consequences

### Positive

* The primary workflow remains simple and easy to learn.
* Lipi is optimized for the intended tablet + stylus environment.
* Handwriting receives appropriate priority as a core interaction.
* Familiar tablet gestures reduce cognitive load.
* Automatic saving reduces anxiety around data loss.
* Doctors retain control over their patient records.
* Themeability allows Lipi to have personality without compromising its professional purpose.
* Sprint 5 remains deliberately small and focused.

### Trade-offs

* Finger-based handwriting is intentionally not a primary interaction target.
* Desktop/non-stylus interaction is not the primary prescription-writing experience.
* A richer theme system introduces future UI-maintenance considerations.
* Historical prescription editing requires additional real-world workflow validation.
* Explicit deletion requires careful destructive-action UX.
