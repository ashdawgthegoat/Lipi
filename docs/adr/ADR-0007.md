# ADR-0007 — Lipi Security Architecture & Threat Model

**Status:** Accepted
**Sprint:** 6 — Security
**Date:** 2026-09-06

---

## 1. Context

Lipi is a local-first, offline-first clinical record application intended primarily for doctors using Android and iOS/iPadOS devices, with iPadOS as a primary target.

Lipi stores sensitive clinical information including patient identity, clinical history, prescriptions, investigation reports, digital handwriting, doctor information, templates, and associated metadata.

Previous architectural decisions established that:

* The doctor owns the Lipi Vault and its contents.
* The Vault is the fundamental unit of storage, backup, and transfer.
* SQLite stores structured metadata and relationships but is not itself the clinical record.
* `.lipi` is the canonical editable clinical document format.
* PDF is a derived export format.
* Lipi operates offline and has no mandatory remote server or cloud service.
* Clinical records must never be silently fabricated, replaced, or reconstructed from incomplete information.
* Autosave is part of the normal clinical workflow.

Sprint 6 establishes the security architecture and threat model that must precede production security implementation.

---

## 2. Security Objectives

Lipi's security architecture shall protect four primary properties:

### Confidentiality

Unauthorized parties should not be able to obtain readable clinical records from stored Lipi data.

### Integrity

Lipi should detect unauthorized modification, corruption, truncation, or incomplete clinical data rather than silently presenting it as valid.

### Availability

Security mechanisms must not unnecessarily prevent the doctor from accessing their own records, and failure during normal storage operations must minimize data loss.

### Authenticity / Provenance

Lipi should be able to distinguish valid application-managed records from malformed, corrupted, or otherwise untrusted data.

Security mechanisms must not create misleading claims of absolute protection.

---

## 3. Threat Model

### 3.1 Assets

The security architecture protects:

* Patient identity
* Patient clinical history
* Previous prescriptions
* Investigation and report data
* Digital handwriting
* `.lipi` documents
* Doctor profile and identity
* Prescription templates
* SQLite metadata
* Vault structure and metadata
* Encryption keys and recovery credentials
* Temporary clinical data
* Exported PDFs
* Backups and transferred Vaults

### 3.2 Threat Actors

The MVP considers:

* A person obtaining physical access to the device
* Another person using an otherwise accessible device
* Someone obtaining a copied Lipi Vault
* Malware operating with normal application/user privileges
* Software or processes capable of modifying stored files
* A recipient or holder of a backup
* Accidental corruption or incomplete data transfer

Future remote/cloud attackers are explicitly outside the MVP threat surface because Lipi has no remote service.

### 3.3 Security Boundary

The primary security boundary is:

**Doctor → Lipi → Lipi Vault → Platform security**

The operating system remains a fundamental trust boundary.

Lipi cannot guarantee confidentiality if the underlying operating system is completely compromised by an attacker capable of observing the application while sensitive data is unlocked.

---

## 4. Security Architecture

Lipi shall protect the Vault using established cryptographic mechanisms rather than custom cryptography.

Conceptually:

```text
Doctor
   │
   ▼
Lipi App
   │
   │ authorized access
   ▼
Protected Lipi Vault
   │
   ├── structured metadata
   ├── `.lipi` documents
   └── attachments
   │
   ▼
Platform-secure key storage
```

The Vault remains an application-managed, doctor-owned data container.

Lipi is responsible for applying the security architecture; the operating system provides platform security facilities such as secure key storage and device authentication.

---

## 5. Vault Encryption

Clinical data stored by Lipi shall be encrypted at rest.

The architecture shall not encrypt individual handwriting strokes independently. The Vault is the primary security boundary.

The cryptographic design shall provide both:

* Confidentiality
* Authenticated integrity

Authenticated encryption or an equivalent established construction shall be used where appropriate.

Lipi shall not:

* Invent cryptographic algorithms
* Use obscurity as encryption
* Hard-code encryption keys
* Store encryption keys directly beside the data they protect
* Derive encryption keys from predictable patient, doctor, or device information

The exact cryptographic library and algorithm parameters are implementation decisions and must be selected from established, maintained cryptographic implementations.

---

## 6. Key Architecture

The Vault shall use a randomly generated Vault encryption key.

The Vault encryption key shall be separate from the doctor's authentication credential.

Conceptually:

```text
Doctor credential
       │
       ▼
Unlock / authorization mechanism
       │
       ▼
Vault Key
       │
       ▼
Encrypted Vault
```

The Vault Key shall not simply be the doctor's PIN or password.

A key hierarchy may use a separate key-encryption mechanism so that the Vault encryption key can be protected by multiple authorized access paths.

The exact hierarchy shall be finalized during implementation based on the selected platform and cryptographic libraries.

---

## 7. Platform Secure Storage

Lipi shall use platform-provided secure key storage facilities where available.

For the MVP:

* Android shall use Android platform secure key-storage facilities such as Android Keystore.
* iOS/iPadOS shall use Apple platform secure key-storage facilities such as Keychain and associated platform security mechanisms.

Platform secure storage protects key material; it does not replace Lipi's own Vault encryption architecture.

Lipi shall not assume that filesystem-level application protection alone constitutes sufficient Vault protection.

---

## 8. Application Authentication

Lipi shall provide an application-access security mechanism.

Where supported, the application should integrate with the device's existing authentication facilities, such as:

* Device PIN/passcode
* Biometrics
* Other appropriate platform authentication mechanisms

Application authentication and Vault encryption are separate security layers.

The purpose of app authentication is to prevent casual or unauthorized access to Lipi through an otherwise accessible device.

The purpose of Vault encryption is to protect stored clinical data even if the Vault itself is copied or accessed outside normal Lipi operation.

---

## 9. Device Migration

The Vault must remain portable between supported devices.

However, the raw Vault encryption key shall not simply be exported as an ordinary file alongside the Vault.

Device migration shall instead provide a secure mechanism through which an authorized doctor can establish Vault access on a new device.

Conceptually:

```text
Old Device
    │
    │ authenticated migration
    ▼
Encrypted Vault
    │
    ▼
New Device
    │
    │ authorized recovery/migration
    ▼
New device secure key storage
```

The doctor should not be required to manually manipulate cryptographic key files.

The exact migration protocol is an implementation decision.

---

## 10. Recovery

Because Lipi is offline-first and has no mandatory remote service, recovery cannot depend upon a Lipi server.

A deliberate offline recovery mechanism shall exist.

The recovery mechanism shall allow an authorized doctor to regain access to their Vault following events such as:

* Forgotten application/Vault credential
* Lost device
* Device replacement
* Device failure
* Restoration from backup

The recovery mechanism must not make Lipi itself the sole authority capable of recovering the doctor's records.

The doctor must retain a recovery capability outside the normal device-local authentication path.

The exact recovery credential format and user experience remain implementation decisions.

---

## 11. `.lipi` Integrity

The `.lipi` format remains the canonical editable clinical document.

Its existing architecture is retained:

```text
consultation_<uuid>.lipi
├── manifest.json
├── ink/
│   └── page-001.inkml
└── templates/
    └── custom_template.png
```

The `.lipi` package shall be treated as structured clinical data rather than merely an image of handwriting.

Potential integrity failures include:

* Modified InkML
* Removed or altered strokes
* Modified manifest
* Replaced template
* Malformed package
* Truncated package
* Missing required resources
* Unauthorized replacement of the entire document

Lipi must detect integrity/format failures and must not silently treat the resulting document as valid.

---

## 12. SQLite Security

SQLite remains metadata infrastructure rather than the authoritative clinical record.

SQLite may contain:

* Internal IDs
* Patient discovery information
* Relationships
* File references
* Search metadata
* Timestamps
* Vault/schema metadata

Lipi shall not blindly trust SQLite references.

If SQLite and the filesystem disagree, Lipi must detect the inconsistency and enter an appropriate safe failure/recovery path.

Lipi must never reconstruct a clinical record from incomplete metadata merely because the corresponding `.lipi` document is unavailable.

---

## 13. Safe Persistence and Autosave

Autosave remains mandatory for normal clinical workflow.

Storage operations shall be designed to minimize corruption from:

* Application crashes
* Device shutdown
* Interrupted writes
* Interrupted transfers
* Filesystem failures

Where practical, Lipi shall use atomic or transactional persistence patterns.

The desired invariant is:

```text
Before successful commit → previous valid state remains available

After successful commit  → new valid state is available
```

A partially written clinical document must never silently replace the last known valid document.

---

## 14. Vault Transfer and Backup

The complete Lipi Vault remains the unit of backup and transfer.

Backups and transfers shall be validated before being adopted as an active Vault.

Validation should establish, where possible:

* Vault structure
* Required components
* Integrity
* Format compatibility
* Document validity
* Completeness of required references

An incomplete transfer shall not be treated as a valid Vault.

Recovery operations should preserve the original Vault whenever possible and perform repair/recovery against a copy rather than destructively modifying the only source.

---

## 15. Failure and Corruption Handling

Lipi shall follow a **fail-closed principle for clinical data**.

If Lipi cannot establish that a record is valid and safely accessible, it shall not present the record as though it were valid.

Examples:

| Failure                | Required behavior                     |
| ---------------------- | ------------------------------------- |
| Valid Vault            | Open normally                         |
| Modified/corrupt Vault | Detect and refuse unsafe access       |
| Corrupt `.lipi`        | Do not silently reconstruct           |
| Missing `.lipi`        | Do not fabricate replacement          |
| Interrupted autosave   | Preserve previous valid state         |
| Interrupted transfer   | Treat destination as incomplete       |
| Invalid backup         | Do not blindly restore                |
| SQLite inconsistency   | Detect and enter safe recovery        |
| Unsupported format     | Refuse safely while preserving source |
| Export failure         | Preserve canonical `.lipi`            |
| Lost device            | Provide migration/recovery path       |
| Forgotten credential   | Provide recovery path                 |

Lipi shall distinguish between **detecting a failure** and **determining its cause**.

An integrity failure must not automatically be reported as evidence of malicious activity.

---

## 16. Export Security Boundary

PDF remains a derived export of the canonical `.lipi` document.

Exporting a PDF constitutes an intentional data boundary crossing:

```text
Protected Lipi Vault
        │
        ▼
      Export
        │
        ▼
       PDF
        │
        ▼
Outside Lipi's security boundary
```

Lipi can protect the generation process and avoid leaving unnecessary temporary copies.

Once a doctor intentionally releases the PDF to another application, storage location, person, messaging service, or external device, Lipi cannot control the security of that copy.

Export must never modify or destroy the canonical `.lipi` document.

---

## 17. Temporary and Derived Data

Clinical information may exist outside the canonical Vault temporarily.

Potential examples include:

* Temporary export files
* Rendering caches
* Thumbnails
* Crash-related data
* Temporary `.lipi` files
* Logs
* Intermediate files

These are considered part of the security surface.

Lipi shall minimize unnecessary sensitive temporary data and shall avoid placing clinical information into logs or other nonessential application artifacts.

---

## 18. Responsibility Boundaries

### Lipi is responsible for:

* Vault encryption
* Cryptographic key lifecycle
* Integrity protection
* Safe persistence
* `.lipi` validation
* Vault validation
* Corruption detection
* Recovery workflows
* Device migration workflows
* Secure handling of temporary data
* Application access controls
* Safe export behavior

### The operating system is responsible for:

* Device security
* Application isolation
* Platform secure key storage
* Device authentication facilities
* Platform/hardware security mechanisms where available

### The doctor is responsible for:

* Device authentication credentials
* Recovery credentials
* Physical access to the device
* Maintaining backups
* Deciding where exported clinical records are sent or stored

These boundaries must remain explicit.

---

## 19. Explicit Non-Goals

The following are outside the Sprint 6 MVP security architecture:

* Cloud authentication
* Cloud synchronization
* Remote Lipi servers
* Hospital multi-user access control
* Enterprise SSO
* Remote administration
* Centralized identity infrastructure
* Network security infrastructure
* AI security architecture
* Centralized audit infrastructure
* Regulatory certification
* Compliance certification claims
* Production penetration testing
* Protection against a completely compromised operating system

These may require separate security architecture if introduced in future versions.

---

## 20. Security Invariants

The following invariants shall guide implementation:

1. **Clinical Vault data is protected at rest.**
2. **Cryptographic secrets are never hard-coded.**
3. **Vault encryption keys are separated from the data they protect.**
4. **Unauthorized modification must be detectable.**
5. **`.lipi` remains the canonical editable record.**
6. **PDF is always derived from `.lipi`.**
7. **Lipi never silently fabricates or replaces clinical records.**
8. **Autosave must not casually destroy the previous valid state.**
9. **Vault transfer and backup must preserve Vault coherence.**
10. **Vault access must remain recoverable without a mandatory remote service.**
11. **The doctor must not need to understand cryptography to use Lipi.**
12. **The Vault remains owned and portable by the doctor.**
13. **Security mechanisms must not unnecessarily interfere with normal clinical workflow.**
14. **Lipi must not claim protection beyond the actual trust boundary of the operating system.**

---

## 21. Deferred Implementation Decisions

The following remain intentionally open for implementation planning and validation:

* Exact cryptographic algorithm and library
* Exact key hierarchy implementation
* Exact key derivation parameters
* Exact recovery credential format
* Exact device migration protocol
* Exact app-lock UX
* Exact temporary-file cleanup behavior
* Exact Vault integrity metadata representation
* Exact atomic-write implementation
* Exact corruption/recovery UI
* Platform-specific secure-storage integration details

These decisions must conform to this ADR rather than changing its security principles without a subsequent architectural decision.

---

## 22. Consequences

### Positive

* Clinical records are protected against common local-storage threats.
* A copied Vault should not expose plaintext clinical data.
* Unauthorized modification can be detected.
* Autosave can remain seamless while being made safer.
* Vault portability remains compatible with encryption.
* Device replacement does not inherently imply data loss.
* Lipi remains offline-first.
* The doctor remains the owner of the Vault.
* The architecture avoids custom cryptography and unnecessary security complexity.
* Security responsibilities are clearly divided between Lipi, the operating system, and the doctor.

### Negative

* Encryption introduces key-management complexity.
* Recovery mechanisms introduce additional security-sensitive design.
* Device migration becomes more complex than copying ordinary files.
* Corruption detection may prevent Lipi from opening a damaged record until recovery occurs.
* Secure temporary-data handling adds implementation complexity.
* Platform-specific security integrations will be required.

These costs are accepted because clinical records require stronger guarantees than ordinary personal notes.

---

## 23. Decision

Lipi shall implement a **local, encrypted, integrity-protected, doctor-owned Vault security architecture**.

The Vault shall be protected using established cryptographic mechanisms, with encryption keys protected through platform secure-storage facilities where available.

Lipi shall distinguish application access from Vault encryption, maintain secure offline recovery and migration paths, detect tampering and corruption, and fail safely rather than silently reconstructing clinical records.

The architecture deliberately avoids mandatory cloud infrastructure, centralized identity, custom cryptography, and security mechanisms that would turn Lipi into the owner or sole recovery authority of the doctor's data.

The governing principle is:

> **Lipi protects the doctor's data without becoming the owner of the doctor's data.**

This ADR establishes the security architecture for implementation and supersedes no prior architectural decision unless explicitly stated above.

---

## 24. Final Sprint 6 Statement

Sprint 6 establishes that Lipi's security model is built around:

**Doctor-owned data → protected Vault → established cryptography → platform-secured keys → integrity verification → safe failure → offline recovery → portable ownership.**

Security is therefore treated as part of Lipi's architecture rather than as a collection of security features added after implementation.
