# ADR-0004 — Vault & Storage Architecture

**Status:** Accepted
**Project:** Lipi
**Sprint:** Sprint 3 — Vault & Storage Architecture

## Executive Summary

Sprint 3 establishes how Lipi stores and manages the doctor's data.

Lipi will use the **operating system's filesystem** as its underlying storage system. A Lipi Vault will be represented as a user-owned directory containing the complete data belonging to that Vault.

A single SQLite database will exist at the Vault level and will contain the minimum structured metadata required for record identity, relationships, file references, and patient discovery.

Actual clinical documents and attachments will remain ordinary files within the Vault.

The objective is to keep storage simple, portable, local-first, and independent of any cloud service or proprietary storage system.

---

## Vault

A **Vault** is the complete collection of data belonging to a Lipi workspace.

The Vault is represented as a directory managed by the operating system's filesystem.

Conceptually:

```text
Lipi Vault/
├── lipi.db
├── patient/
├── doctor/
├── documents/
└── attachments/
```

The exact directory structure may evolve during implementation, but the Vault itself remains the fundamental unit of user-owned data.

The Vault is not a cloud resource and does not require a Lipi account.

---

## Storage Architecture

Lipi uses a hybrid filesystem and SQLite architecture.

```text
                    LIPI VAULT
                        │
             ┌──────────┴──────────┐
             │                     │
          lipi.db             OS Filesystem
             │                     │
      Structured metadata       Actual files
      Relationships             .lipi documents
      Search indexes            PDFs
      File references           Images
      Internal IDs              Reports
```

### SQLite

SQLite is responsible for structured information required by Lipi to organize and retrieve records.

This includes:

* Internal record identifiers
* Patient discovery fields
* Relationships between records
* References to stored documents and attachments
* Relevant timestamps and metadata
* Search indexes
* Vault and schema metadata

SQLite is an implementation and infrastructure component.

It is **not** the clinical record itself.

### Filesystem

The operating system filesystem stores the actual user data and documents.

This includes:

* `.lipi` documents
* PDF files
* Images
* Scan and investigation reports
* Other supported attachments

Lipi does not introduce a custom filesystem.

---

## Internal Identity

Every persistent record requiring an identity will have an internal identifier.

This identifier exists for machine-level integrity and relationships.

It is not intended to become a human-facing patient number.

For example:

```text
Patient
├── Internal ID: <immutable identifier>
├── Name: Ravi Kumar
├── Date of Birth: ...
└── ...
```

The internal identifier allows Lipi to distinguish records even when multiple patients have identical or similar identifying information.

---

## Patient Discovery

Patient discovery is treated as a **search problem**, not as a unique-number problem.

The doctor may search using available patient information such as:

* Name
* Date of birth
* Other supported identifying information

Additional searchable fields may be introduced where justified by the clinical workflow.

Lipi presents matching records to the doctor.

The doctor selects the appropriate patient.

Lipi must not infer or silently determine which patient the doctor intended.

This follows the architectural principle established in Sprint 1:

> **Doctor decides. Assist, never assume.**

---

## Minimal Structured Metadata

SQLite should contain only the structured information necessary for Lipi to:

* Maintain record identity
* Maintain relationships
* Locate associated files
* Support useful patient discovery
* Maintain the integrity of the Vault

Lipi should avoid duplicating information unnecessarily between SQLite and the actual clinical documents.

The database must not become a second version of the patient's clinical record.

The MVP should therefore prefer a minimal SQLite representation rather than attempting to model every piece of clinical information as database fields.

---

## Clinical Documents

The `.lipi` format established during Sprint 0 remains the canonical editable representation of handwritten clinical documents.

The `.lipi` file itself remains a filesystem object.

SQLite may contain metadata and a reference to the corresponding `.lipi` file, but the handwritten document is not required to be stored inside SQLite.

Standard formats such as PDF, SVG, and PNG remain export formats.

---

## Attachments

Clinical attachments remain filesystem objects.

Examples include:

* PDFs
* Images
* Scan reports
* Investigation reports
* Other supported clinical files

SQLite maintains the metadata and relationships necessary for Lipi to locate and present these files.

The actual binary contents remain outside the database.

---

## Backup and Transfer

The **complete Vault is the unit of backup and transfer**.

Lipi should provide an application-level **Backup / Transfer Vault** operation suitable for tablet environments.

The operation produces a complete, self-contained copy of the Vault.

The original Vault remains unchanged.

The resulting copy may be transferred to user-controlled external storage such as:

* USB drives
* External SSDs
* SD cards
* Other accessible storage

The transferred Vault can subsequently be opened or imported by Lipi on another supported device.

No Lipi account or cloud service is required.

### Transfer Invariant

A valid Lipi Vault must remain a coherent, transferable unit.

The doctor should not need to manually understand or manipulate the SQLite database, individual document references, or internal identifiers to transfer their data.

The implementation must ensure that the SQLite metadata and referenced filesystem contents correspond correctly in the generated transfer copy.

---

## Data Ownership

The doctor owns the Vault and the data contained within it.

Lipi does not require the doctor's clinical records to be stored on a remote server.

Cloud synchronization remains outside the scope of this architecture.

The storage architecture therefore does not make Lipi's continued operation dependent upon an external service.

---

## Versioning

The SQLite schema and other persistent storage structures must be versioned.

A Vault should contain sufficient metadata for Lipi to determine which storage schema it uses.

Future Lipi releases may migrate older Vaults to newer storage schemas when necessary.

The existence of a migration mechanism does not imply that the fundamental Vault concept changes between releases.

The goal is for future versions of Lipi to evolve around existing user data rather than repeatedly restructuring or replacing the user's underlying storage model.

---

## Portability

A Lipi Vault is designed to be portable across supported platforms.

The storage architecture therefore avoids dependence on:

* A specific operating system filesystem format
* A proprietary cloud service
* A Lipi account
* A platform-specific database server

Platform-specific filesystem access mechanisms may differ, particularly on mobile operating systems, but the logical Vault remains platform-independent.

---

## Deferred Decisions

The following remain outside the scope of Sprint 3:

* Final `.lipi` file specification
* Encryption implementation
* Cloud synchronization
* Hospital workflows
* AI
* Clinical decision support
* Advanced clinical search
* Plugin architecture
* Detailed backup implementation
* Detailed migration implementation

These should be addressed only when their respective requirements are established.

---

## Design Principles Established

Sprint 3 establishes the following principles:

1. **The OS filesystem is Lipi's underlying storage system.**
2. **The Vault is the fundamental unit of user-owned data.**
3. **One SQLite database exists at the Vault level.**
4. **SQLite stores minimal structured metadata rather than the complete clinical record.**
5. **Actual documents and attachments remain filesystem files.**
6. **Internal identifiers exist for machine integrity, not human-facing patient identification.**
7. **Patient discovery is performed through search and confirmed by the doctor.**
8. **The complete Vault must be transferable without cloud dependency.**
9. **Persistent storage structures must be versioned for future migration.**
10. **Future Lipi releases should extend the stable storage foundation rather than repeatedly replace it.**

---

## Conclusion

Sprint 3 establishes a deliberately simple storage architecture for Lipi.

A Lipi Vault is a user-owned directory on the operating system filesystem. A single SQLite database provides the structured metadata, relationships, identifiers, and search capabilities required by the application, while actual clinical documents and attachments remain ordinary files within the Vault.

This architecture avoids both extremes: Lipi does not attempt to manage a custom filesystem, while also avoiding the complexity of implementing database functionality through large collections of independent structured files.

The resulting architecture provides a practical foundation for local ownership, offline operation, portability, backup, and long-term evolution.

The Vault belongs to the doctor.

Lipi is simply the application that understands it.
