# ADR-0005 — Lipi Clinical Document Specification

**Status:** Accepted
**Date:** 2026-09-05
**Sprint:** Sprint 4 — Lipi Document Specification

---

## 1. Context

Lipi is a handwriting-first, local-first, offline-first clinical prescription application.

Sprint 4 was undertaken to validate the concrete document representation required for prescriptions: how a prescription is represented while being edited, how handwritten ink is persisted, how templates are associated with the document, how historical prescriptions are reopened and edited, and how the same document is exported to PDF.

The prototype was deliberately validated on physical Android hardware rather than relying only on automated tests.

All three validation passes were completed successfully:

* Pass 1 / 1B — template asset pipeline and visibility
* Pass 2 — unified prescription zoom and coordinate space
* Pass 3 — historical reopen/edit and faithful PDF export

The final prototype was physically verified on a OnePlus Pad 2 and reached 27/27 automated tests with clean static analysis.
The prototype also established several implementation findings that materially affect the document specification:

* The prescription template and handwritten ink must occupy one shared document coordinate system.
* Viewport zoom and pan must remain view transforms and must not modify stored document geometry.
* Historical prescriptions must remain visually and semantically stable even if the active doctor's profile changes.
* Export must render the same finite document rather than reconstructing handwriting onto an unrelated generic page.
* The editable source must remain vector/digital ink rather than a flattened image.

---

## 2. Decision

Lipi will use a **ZIP-based `.lipi` document format** as the canonical editable representation of a clinical prescription.

A `.lipi` file represents one consultation/prescription and is a self-contained document package.

The canonical structure is:

```text
consultation_<uuid>.lipi
├── manifest.json
├── ink/
│   └── page-001.inkml
└── templates/
    └── custom_template.png
```

The `templates/` entry is present when the prescription uses a custom template. Default/generic templates are reconstructed from the document's stored document/doctor data rather than depending on the current active doctor profile.

The `.lipi` package is the editable clinical document. PDF is an export representation, not the canonical source.

---

## 3. Document Manifest

The package contains exactly one manifest:

```text
manifest.json
```

There is no separate `document.json`.

The manifest contains the minimum document metadata required to reconstruct the prescription, including:

```json
{
  "format": "lipi",
  "version": 1,
  "consultation_id": "...",
  "page": {
    "width": ...,
    "height": ...,
    "unit": "..."
  },
  "patient_snapshot": { ... },
  "doctor_snapshot": { ... },
  "ink": "ink/page-001.inkml"
}
```

The exact implementation may evolve while the prototype remains the reference for the minimum required fields.

### Patient identity

`patient_id` is **not stored in the `.lipi` manifest**.

Association with the patient is provided by the patient workspace and filesystem location in the Lipi Vault.

The consultation/document identifier is sufficient inside the package.

---

## 4. Historical Snapshots

A prescription is a historical clinical document.

Therefore, the document stores the relevant patient and doctor information needed to preserve its historical state.

When reopening an existing `.lipi` document:

1. embedded template data takes precedence over the currently active template;
2. stored doctor information takes precedence over the current doctor profile where required for document reconstruction;
3. the document is reconstructed from its own package contents.

This prevents historical prescriptions from changing merely because a doctor later changes clinics, qualifications, or prescription templates.

## The prototype demonstrated this behavior by switching the active doctor profile and successfully reopening an older prescription with its original embedded custom template intact.

## 5. Prescription Page Model

Each prescription is a **finite page**, not an infinite canvas.

The document has explicit page dimensions and a stable document coordinate system.

The canonical document coordinate space is independent of:

* screen resolution
* display DPI
* WebView size
* viewport zoom
* viewport pan

The editor may transform this document for display, but the stored document geometry does not change.

---

## 6. Digital Ink Representation

Handwritten content is stored as digital vector ink using a minimal subset of W3C InkML.

The canonical ink representation contains the information necessary to reconstruct handwritten strokes while avoiding web-editor-specific application state.

The prototype established a bidirectional mapping:

```text
Excalidraw freedraw elements
        ↕
      InkML
```

The representation preserves, at minimum:

* stroke order
* stroke geometry
* pressure where available
* stroke width
* color

On reopen, InkML is converted back into live Excalidraw freedraw elements.

Historical prescriptions therefore remain editable rather than becoming flattened images. The prototype verified reopening, erasing, adding new strokes, undo/redo, and re-export.

---

## 7. Template Model

The prescription template is owned by the Doctor Domain during setup.

A doctor may use:

1. a custom uploaded prescription template, or
2. the default/generic Lipi template.

The selected template is treated as the **visual page backing** of the prescription.

For custom templates, the template binary is embedded inside the `.lipi` package so the document is self-contained.

The editor renders:

```text
Template layer
      ↓
Handwriting / interactive ink layer
```

The template is never flattened together with handwriting in the canonical editable representation.

---

## 8. Shared Coordinate System

The prescription template and handwritten ink must share one document coordinate system.

The prototype established an **Excalidraw Camera Master** model:

```text
Prescription viewport
└── Single document transform
    ├── Template/page layer
    └── Excalidraw ink layer
```

Excalidraw owns the viewport camera.

Template presentation is synchronized to the same camera transform.

Zoom and pan therefore affect the entire prescription consistently while stored document coordinates remain unchanged.

A zoom operation must never rewrite stored stroke coordinates.

This preserves both:

* accurate stylus input, and
* exact template/ink registration.

## Physical testing verified correct alignment while zooming, panning, and continuing to write at high zoom, with no observed pen parallax or document drift.

## 9. WebView and Offline Template Delivery

The prescription editor runs as a bundled web application inside Android WebView.

The prototype showed that loading the editor through `file:///android_asset/...` caused Chromium origin/CORS failures for module scripts and stylesheets.

The adopted solution is an internal loopback HTTP asset server bound to:

```text
127.0.0.1
```

The bundled editor and runtime template assets are served through this local origin.

This solution:

* remains fully offline,
* avoids external network dependencies,
* gives Chromium a valid HTTP origin,
* avoids Android Binder size problems caused by large base64 payloads,
* allows runtime template images to be streamed locally.

## The prototype physically verified successful loading of both custom and default templates.

## 10. Persistence and Reopen

Closing a prescription automatically persists the current editable state into `.lipi`.

Reopening a `.lipi` reconstructs:

* the finite prescription page,
* stored template,
* relevant typed information,
* doctor/patient snapshots,
* handwritten digital ink.

The reconstructed ink is live and editable.

The document is not reopened as a flattened screenshot or PDF.

---

## 11. Historical Prescription Editing

A prescription selected from patient history may be opened as an editable document.

The workflow is:

```text
Patient
  ↓
Prescription history
  ↓
Select prescription
  ↓
Open .lipi
  ↓
Reconstruct template + ink
  ↓
Edit/add handwriting
  ↓
Save back to document
```

Existing historical content must remain intact while new changes are added.

The prototype verified editing of both default-template and custom-template historical prescriptions, followed by saving and re-exporting.

---

## 12. PDF Export

PDF is an **export format**, not the canonical clinical representation.

The PDF exporter renders the canonical finite document directly.

The export process is conceptually:

```text
.lipi document
    ↓
canonical document coordinates
    ↓
selected template/page
    ↓
typed document fields
    ↓
vector handwritten ink
    ↓
PDF
```

The exporter must not:

* use screen coordinates,
* use the current viewport zoom,
* use the current pan position,
* rely on arbitrary layout margins,
* place ink onto an unrelated generic page,
* mutate the underlying `.lipi` coordinates.

The PDF coordinate transform explicitly maps the canonical document coordinate system to PDF page coordinates, including page scale, origin, and axis direction.

## The prototype demonstrated correct registration for default and custom templates, including export after historical reopening and editing.

## 13. Document Self-Containment

A `.lipi` prescription must be **hermetic** with respect to the resources required to reconstruct its historical appearance.

A custom template therefore belongs inside the `.lipi` package rather than being referenced only through the current doctor's template path.

This ensures:

```text
Old prescription
      +
original template
      +
original document metadata
      +
original ink
      ↓
same historical prescription later
```

The active doctor's current template must not silently replace the template of an old document.

---

## 14. Versioning

The `.lipi` format contains a format version:

```json
"version": 1
```

Versioning applies to the document/package specification rather than to transient editor application state.

Future versions may introduce new fields or package entries, but version changes must preserve the ability to identify and migrate older documents where necessary.

The initial format is intentionally minimal and should not acquire fields merely for speculative future use.

---

## 15. Corruption and Recovery

The `.lipi` package is a filesystem artifact and therefore may become unavailable or corrupted independently of the SQLite database.

The architecture therefore treats:

* SQLite as structured discovery/index metadata, and
* `.lipi` as the clinical document itself.

A missing or unreadable `.lipi` must not be silently reconstructed from incomplete SQLite metadata and must not be replaced with a misleading blank prescription.

Future production hardening should add explicit validation and recovery behavior for malformed packages while preserving the canonical document boundary established here.

---

## 16. Ownership and Domain Boundaries

The following ownership model is established:

### Doctor Domain

Owns:

* doctor identity/profile
* doctor template configuration
* doctor preferences relevant to prescription presentation

### Patient Domain

Owns:

* patient record
* patient discovery/search metadata
* consultation/history relationships

### Application Domain

Coordinates:

* doctor setup
* patient selection
* prescription creation
* prescription reopening
* export workflow

The application coordinates domain interactions; individual domains should not directly modify one another's records.

---

## 17. Consequences

### Positive

This decision provides:

* a canonical editable document representation;
* durable historical prescriptions;
* template self-containment;
* editable historical handwriting;
* deterministic PDF export;
* stable document coordinates;
* viewport-independent storage;
* offline operation;
* separation between clinical documents and database metadata;
* minimal dependence on Excalidraw-specific application state.

It also allows Lipi to preserve the doctor's original prescription appearance while keeping handwritten content independently editable.

### Negative / Trade-offs

The format introduces some complexity:

* `.lipi` requires packaging/unpackaging logic;
* template binaries increase package size;
* InkML conversion must remain compatible with the supported ink subset;
* the PDF exporter must maintain a correct document-to-PDF coordinate transform;
* the Android WebView requires local asset delivery infrastructure;
* production performance and gesture latency still require further optimization.

These trade-offs are accepted because they preserve the core document model and offline-first requirements.

## 19. Out of Scope for This ADR

The following remain implementation and production-hardening concerns rather than changes to the document specification:

* handwriting latency optimization;
* rendering performance optimization;
* production APK size optimization;
* broader UX polish;
* backup/synchronization mechanisms;
* advanced corruption recovery;
* release-build hardening;
* generalized prescription-template design.

The prototype's current latency characteristics are therefore not treated as a reason to change the document architecture.

---

## 20. Final Decision

**Accepted.**

The Sprint 4 prototype establishes the Lipi prescription as a finite, self-contained, editable clinical document represented by a ZIP-based `.lipi` package.

Its canonical editable content consists of:

```text
document metadata
+
historical patient/doctor snapshots
+
prescription template/page
+
canonical digital ink
```

The template and ink share one document coordinate system.

The current viewport is not part of the stored document.

`.lipi` is the canonical editable clinical representation.

PDF is a derived export representation.

Patient association remains external to the `.lipi` package through the patient workspace/Vault context.

This specification is the architectural baseline for subsequent Lipi implementation and production hardening work.
