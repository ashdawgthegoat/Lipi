# ADR-0008 — Lipi MVP Implementation Architecture

* **Status:** Accepted
* **Date:** 2026-09-06
* **Decision Type:** Implementation Architecture
* **Scope:** Lipi MVP
* **Supersedes:** None
* **Depends On:** ADR-0001 through ADR-0007

---

# 1. Context

Lipi's previous architecture decisions established:

* Excalidraw as the handwriting/editor foundation;
* a domain-oriented application architecture;
* a Patient Domain, Doctor Domain, and Consultation Domain;
* a user-owned Vault;
* SQLite for structured metadata;
* `.lipi` as the canonical editable clinical document format;
* vector ink represented through a minimal InkML-compatible model;
* finite document coordinates independent of viewport state;
* automatic persistence;
* local-first/offline-first operation;
* encrypted Vault storage;
* fail-closed behavior;
* explicit historical prescription semantics.

Those decisions define what Lipi must preserve.

Sprint 7 translated those decisions into an implementation contract, technology stack, build sequence, and completion criteria.

The project now requires a concrete implementation architecture that can be used to begin MVP development without reopening settled architectural decisions.

---

# 2. Decision

Lipi MVP will use a **layered, domain-oriented Flutter architecture with explicit application workflows and replaceable infrastructure adapters**.

The implementation will be structured around:

```text
Presentation
      ↓
Application
      ↓
Domain
      ↑
Infrastructure
```

The application will use:

* Flutter/Dart for the application;
* native platform WebViews for the bundled handwriting editor;
* Excalidraw as the initial editor implementation;
* an internal loopback HTTP server for bundled editor assets/runtime;
* SQLite with SQLCipher for structured Vault metadata;
* filesystem-backed Vault storage behind an abstraction;
* `.lipi` as the canonical editable document package;
* a Lipi-owned canonical document model;
* InkEngine as the boundary between Lipi and Excalidraw;
* AES-GCM-based authenticated encryption for protected file content;
* platform secure storage for protected key material;
* canonical-document-based PDF rendering.

The implementation will be dependency-ordered according to `BUILD-PLAN.md`.

# 4. Domain Architecture

## 4.1 Patient Domain

The Patient Domain owns:

* patient identity;
* patient information;
* clinical history;
* medication history;
* allergy information;
* patient/consultation relationships.

It does not own storage technology.

## 4.2 Doctor Domain

The Doctor Domain owns:

* doctor identity;
* doctor profile;
* active prescription template;
* doctor preferences.

Current configuration is mutable.

Historical configuration required by a consultation is captured as part of the consultation's document snapshot.

## 4.3 Consultation Domain

The Consultation Domain owns:

* consultation identity;
* prescription lifecycle;
* canonical clinical document state;
* historical consultation behavior.

## 4.4 Application Layer

The Application layer coordinates operations involving multiple domains or infrastructure services.

Examples:

```text
CreatePatient
StartConsultation
SaveConsultation
LoadConsultation
SearchPatients
ListConsultationHistory
DeletePatient
ConfigureDoctor
ConfigureTemplate
ExportConsultation
```

Application workflows may depend on domain interfaces and infrastructure ports.

They must not expose infrastructure details to presentation code unnecessarily.

# 5. Infrastructure Architecture

Infrastructure is divided by responsibility.

```text
infrastructure/
├── vault/
├── database/
├── documents/
├── ink/
├── export/
├── security/
├── filesystem/
└── platform/
```

## Vault

Coordinates:

* Vault lifecycle;
* Vault initialization;
* opening/closing;
* validation;
* protected storage coordination.

## Database

Owns:

* SQLite connection;
* SQLCipher configuration;
* schema;
* migrations;
* transactions;
* metadata repositories.

## Documents

Owns:

* `.lipi` serialization;
* `.lipi` deserialization;
* manifest validation;
* package validation;
* document repository behavior.

## Ink

Owns:

* InkEngine;
* Excalidraw adapter;
* WebView bridge;
* editor runtime hosting;
* canonical ink conversion.

## Export

Owns:

* PDF rendering;
* export-specific document traversal.

## Security

Owns:

* Vault key lifecycle;
* cryptographic operations;
* secure storage integration;
* integrity verification.

## Filesystem

Owns:

* Vault filesystem access;
* paths;
* directory creation;
* file replacement;
* file reads/writes.

## Platform

Owns platform-specific behavior that cannot reasonably remain platform-neutral.

# 6. Canonical Document Architecture

Lipi will maintain a Lipi-owned canonical clinical document model.

The relationship is:

```text
Clinical Workflow
       ↓
Canonical Lipi Document
       ↓
┌──────┴────────┐
↓               ↓
.lipi           PDF
```

The canonical model is not:

* an Excalidraw scene;
* a SQLite row;
* a Flutter widget tree;
* a screenshot;
* a PDF.

Derived representations must not become authoritative.

---

# 7. `.lipi` Architecture

`.lipi` remains the canonical editable document format established by ADR-0005.

A version-1 package has the conceptual structure:

```text
consultation_<uuid>.lipi/
├── manifest.json
├── ink/
│   └── page-001.inkml
└── templates/
    └── custom_template.png
```

The actual format remains ZIP-based.

The implementation will provide:

```text
LipiDocumentSerializer
LipiDocumentDeserializer
LipiPackageValidator
```

The serializer operates on the canonical Lipi document model.

The editor is not permitted to define `.lipi` semantics.

---

# 8. Storage Representation

A distinction is made between:

### Logical `.lipi`

The canonical document format remains a valid ZIP-based `.lipi` package.

### Protected Vault representation

When stored inside an encrypted Vault, the canonical `.lipi` bytes may be wrapped in an authenticated encrypted storage envelope.

Conceptually:

```text
Canonical Lipi Document
        ↓
.lipi ZIP bytes
        ↓
Authenticated encryption envelope
        ↓
Protected Vault storage
```

On read:

```text
Protected Vault storage
        ↓
Integrity/authentication verification
        ↓
Decryption
        ↓
.lipi bytes
        ↓
Validation
        ↓
Canonical Lipi Document
```

This preserves the canonical `.lipi` specification while satisfying the Vault's at-rest protection requirement.

Plaintext `.lipi` data should exist only transiently when required for processing.

---

# 9. Database Architecture

SQLite is infrastructure and stores structured metadata.

SQLCipher provides database encryption.

The database may contain:

* patient metadata;
* doctor metadata;
* consultation metadata;
* relationships;
* document references;
* Vault/schema metadata;
* search indexes.

The database must not become the canonical representation of handwritten prescriptions.

The document repository must refuse to silently fabricate a missing `.lipi` from database metadata.

---

# 10. Filesystem Architecture

All Vault filesystem access must pass through a Lipi-owned abstraction.

Conceptually:

```text
Application
    ↓
Vault / Repository Interface
    ↓
VaultFilesystem
    ↓
dart:io
```

Application/domain code must not scatter direct filesystem operations.

The physical directory structure may use opaque UUID-based paths to reduce unnecessary metadata exposure.

The exact physical layout may evolve without changing the logical Vault contract.

---

# 11. Ink Architecture

The handwriting system will use an `InkEngine` abstraction.

Conceptually:

```text
Canonical Lipi Document
          ↕
      InkEngine
          ↕
 Excalidraw Adapter
          ↕
       WebView
```

The canonical ink representation is Lipi-owned.

Excalidraw is an implementation adapter.

This permits future replacement of the editor without requiring the clinical domain or `.lipi` format to become Excalidraw-specific.

---

# 12. WebView Architecture

The bundled Excalidraw editor will run inside the platform WebView.

The validated asset-serving architecture is:

```text
Flutter Application
       ↓
Loopback HTTP Server
       ↓
127.0.0.1:<ephemeral-port>
       ↓
Bundled Editor Assets
       ↓
WebView
```

The application will not rely on:

```text
file:///android_asset/...
```

for the bundled editor runtime.

The loopback server exists solely to provide the bundled local runtime and assets.

No external network connection is required.

---

# 13. Editor Bridge

Communication between Flutter and the editor will use a Lipi-owned bridge.

The bridge may exchange:

* document initialization;
* canonical ink;
* editor commands;
* stroke updates;
* template state;
* save/flush requests;
* editor status/errors.

Arbitrary Excalidraw application state must not become the application's global state.

The bridge is an adapter boundary.

---

# 14. Coordinate Architecture

Lipi defines a finite canonical document coordinate system.

Viewport state is separate:

```text
Canonical Document Coordinates
             ↓
       Editor Camera
             ↓
       Screen Coordinates
```

Zoom and pan modify the camera.

They do not modify canonical document coordinates.

All persistence and export operate on canonical coordinates.

---

# 15. Template Architecture

The Doctor Domain owns current template configuration.

A consultation stores the historical template information required to reproduce the prescription.

Therefore:

```text
Current Template
      ↓
Doctor Domain

Historical Template
      ↓
Consultation / .lipi
```

Changing the current template must not modify historical prescriptions.

Custom template resources required by historical documents are embedded in the `.lipi` package.

---

# 16. Snapshot Architecture

When a consultation is created, the document captures the relevant patient and doctor snapshots.

The purpose is historical fidelity.

Conceptually:

```text
Current Patient ──────┐
                      ├──→ Consultation Snapshot
Current Doctor ───────┤
                      │
Current Template ────┘
```

Later profile/template changes must not silently alter the historical consultation.

---

# 17. Persistence Architecture

Clinical document persistence follows:

```text
Editor
  ↓
Canonical Document
  ↓
Serializer
  ↓
Protected Storage
```

A successful save must result in a valid durable document.

A failed save must preserve the previous valid document whenever technically possible.

Document replacement must use atomic or equivalent safe replacement semantics.

---

# 18. Autosave Architecture

Autosave is coordinated by the application/infrastructure persistence boundary.

Conceptually:

```text
Editor Change
      ↓
Canonical Document Update
      ↓
Autosave Scheduler
      ↓
Serializer
      ↓
Safe Replacement
      ↓
Persisted Document
```

The editor itself does not own persistence.

The database does not replace the document save.

Autosave must never knowingly replace a valid document with an invalid partial representation.

---

# 19. Security Architecture

The security implementation will use established cryptographic libraries.

The intended cryptographic architecture includes:

* AES-256-GCM for authenticated content encryption;
* Argon2id where password-based key derivation is required;
* HKDF where hierarchical key derivation is required;
* platform secure storage for protected key material.

No cryptographic primitive will be implemented manually.

The Vault encryption key is distinct from the user's authentication credential.

---

# 20. Key Storage

The application will use a security abstraction rather than coupling the application to a platform-specific key store.

Conceptually:

```text
VaultKeyStore
      ↓
SecureStorage Adapter
      ↓
Android Keystore / iOS Keychain
```

The application must not store the raw Vault encryption key as an ordinary plaintext file.

---

# 21. Authentication vs Encryption

Authentication answers:

> Is this user/application authorized to unlock the Vault?

Encryption answers:

> Can the protected Vault contents be decrypted and authenticated?

These are related but separate responsibilities.

Do not use an authentication password directly as the storage encryption key.

Where password-based unlocking is required, use the defined password derivation mechanism.

---

# 22. Error Architecture

Infrastructure failures must be translated into application-understandable errors.

Examples:

```text
VaultError
StorageError
DocumentError
SerializationError
SecurityError
ExportError
EditorError
MigrationError
```

Errors must preserve enough information for:

* user-facing recovery;
* debugging;
* safe failure;
* test verification.

Sensitive data must not be embedded in errors or logs unnecessarily.

---

# 23. Fail-Closed Architecture

If Lipi cannot establish document validity, it must not present the document as valid.

This applies to:

* decryption failure;
* integrity failure;
* malformed `.lipi`;
* unsupported version;
* missing required resources;
* corrupted Vault;
* failed migration.

The system must prefer:

```text
Reject
→ Preserve
→ Explain
→ Recover
```

over:

```text
Guess
→ Reconstruct
→ Continue
```

---

# 24. Export Architecture

PDF export consumes the canonical document model.

```text
.lipi
 ↓
Canonical Document
 ↓
PdfExporter
 ↓
PDF
```

The exporter must not depend on:

* current editor viewport;
* screen coordinates;
* editor screenshot;
* Excalidraw rendering output.

PDF export is a derived operation.

A failed export must not modify the canonical clinical document.

---

# 25. Application Workflow Architecture

The principal workflow is:

```text
First Launch
    ↓
Doctor Setup
    ↓
Template Setup
    ↓
Patient Creation/Search
    ↓
Patient Workspace
    ↓
New Prescription
    ↓
Stylus Writing
    ↓
Automatic Save
    ↓
Close/Reopen
    ↓
Prescription History
    ↓
Optional PDF Export
```

The Application layer owns orchestration.

Presentation code triggers workflows rather than directly manipulating multiple domains and repositories.

---

# 26. Historical Editing Architecture

The application must explicitly distinguish:

```text
View Historical Prescription
Create New Prescription From Context
Edit Existing Historical Prescription
```

These are separate application operations.

Historical editing must be intentional.

The system must not interpret opening an old prescription as permission to modify it.

---

# 27. Patient Deletion Architecture

Deletion is an explicit destructive application workflow.

The presentation layer must request the operation.

The Application layer coordinates the deletion.

The underlying repositories perform the necessary persistence operations.

The operation must not be triggered by accidental navigation.

---

# 28. Platform Architecture

Flutter remains the primary application framework.

Android tablet is the current physical validation platform.

iPadOS remains a first-class target, but physical iPad validation is currently deferred because appropriate hardware is unavailable.

The architecture therefore requires:

* platform-specific code isolation;
* no Android-specific dependencies in domain code;
* no Android-specific filesystem assumptions in application/domain code;
* replaceable platform adapters where necessary.

The absence of current iPad hardware does not justify deliberate Android-only architecture.

---

# 29. Testing Architecture

Testing will occur at multiple levels.

```text
Domain
  ↓
Application
  ↓
Persistence
  ↓
Document
  ↓
Security
  ↓
Integration
  ↓
Physical Device
  ↓
Dad Test
```

Each layer must test its own invariants.

Important properties include:

* domain correctness;
* persistence durability;
* `.lipi` round-trip;
* coordinate preservation;
* historical snapshot preservation;
* autosave safety;
* encryption/integrity;
* export correctness;
* workflow correctness.

---

# 30. Physical Validation

Android tablet validation is mandatory for the MVP.

Physical testing must cover:

* stylus input;
* finger navigation;
* zoom;
* pan;
* editor startup;
* autosave;
* restart/reopen;
* historical prescriptions;
* PDF export;
* Vault/security behavior;
* prolonged normal use.

iPadOS physical validation is deferred until appropriate hardware is available.

The project must never claim that iPad physical validation has passed before it actually occurs.

# 33. Consequences

## Positive

### Clear ownership

Clinical concepts have explicit owners.

### Durable records

The canonical document is independent of the UI and editor.

### Replaceable infrastructure

The database, editor, WebView, filesystem implementation, and export implementation can evolve independently.

### Offline reliability

The architecture does not depend on a remote service.

### Historical fidelity

Snapshots and embedded resources preserve historical context.

### Testability

Domain behavior can be tested without Flutter or platform dependencies.

### Security boundaries

Vault, database, document, and key-management responsibilities are explicit.

### Controlled complexity

The implementation begins with the minimum architecture required for the MVP.

---

# 34. Costs and Tradeoffs

## More Interfaces

Explicit boundaries create additional interfaces and adapters.

This is accepted because they protect important architectural boundaries.

## More Serialization Work

Lipi maintains its own canonical document representation rather than storing editor-native state.

This is accepted because the clinical record must not depend on the editor.

## More Persistence Complexity

Safe autosave and encrypted storage require more work than simply writing files.

This is accepted because data durability is a core requirement.

## Platform Work

Flutter reduces shared application work, but WebView, secure storage, filesystem behavior, and hardware input still require platform validation.

This is accepted.

## Current iPad Validation Gap

The architecture targets iPadOS, but physical validation cannot currently be performed.

This is explicitly accepted as a temporary validation limitation, not as a change to the target platform.

---

# 35. Rejected Alternatives

## Excalidraw as Canonical Storage

Rejected.

The editor must remain replaceable and cannot own clinical document semantics.

## SQLite as Canonical Clinical Storage

Rejected.

SQLite stores structured metadata and references. The `.lipi` document remains authoritative.

## PDF as Canonical Storage

Rejected.

PDF is a derived export format and does not preserve the editable canonical representation.

## Screenshot-Based Persistence

Rejected.

Screenshots cannot provide the required canonical vector/editable representation.

## Cloud-First Architecture

Rejected.

The MVP is local-first/offline-first and must operate without Lipi infrastructure.

## Direct Filesystem Access Throughout the Application

Rejected.

This would leak storage concerns across the architecture.

## Domain Depending on Flutter

Rejected.

The domain must remain technology-independent.

## Domain Depending on Excalidraw

Rejected.

Excalidraw is an infrastructure/editor implementation.

## Custom Cryptography

Rejected.

Established cryptographic primitives and maintained libraries are required.

## Premature Plugin Architecture

Rejected.

No generalized plugin system is required by the MVP.

## Premature Hospital Architecture

Rejected.

Hospital-scale multi-user workflows are explicitly outside MVP scope.

---

# 36. Migration and Future Evolution

This architecture deliberately permits future changes without requiring them now.

Potential future work includes:

* additional editor engines;
* cloud synchronization;
* hospital workflows;
* multi-user access;
* advanced recovery;
* additional export formats;
* AI-assisted features;
* Linux-first workflows;
* additional platform integrations.

These are not architectural commitments of the MVP.

Future functionality must integrate through the existing boundaries rather than bypassing them.

---

# 37. Implementation Authority

Once accepted, this ADR establishes the implementation architecture for the Lipi MVP.

Implementation details may change when they do not alter architectural intent.

Examples of implementation details that may change:

* class names;
* private helper structure;
* exact repository method names;
* physical directory naming;
* UI widget composition;
* internal autosave timing;
* internal caching;
* test organization.

Changes that affect:

* canonical data ownership;
* `.lipi` semantics;
* security architecture;
* dependency direction;
* editor boundary;
* Vault authority;
* persistence authority;

require architectural review and, where appropriate, a new or amended ADR.

---

# 38. Final Decision

Lipi MVP will be implemented as a:

> **local-first, domain-oriented Flutter application with a Lipi-owned canonical clinical document model, a user-owned encrypted Vault, explicit application workflows, and replaceable infrastructure adapters.**

The architecture prioritizes:

```text
Clinical correctness
      ↓
Data durability
      ↓
Security
      ↓
Offline reliability
      ↓
Workflow usability
      ↓
Replaceability
      ↓
Future extensibility
```

It intentionally avoids speculative complexity until the product requires it.

**This ADR closes the architecture-planning phase of Sprint 7.**
